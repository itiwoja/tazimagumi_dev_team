# 詳細設計書：概念→商品の絞り込み導線 v0.1

**プロジェクト：** 田島組 卒業制作（男の身だしなみアプリ）
**対象機能：** S2 ロードマップの各概念ステップから S3 該当カテゴリへの直接遷移
**版：** v0.1 / 2026-08-31（**チーム合意前の提案ドラフト**。実装決定ではない）
**根拠：** [プロダクト改善意見 v0.1](./プロダクト改善意見_v0.1.md) §1 強み3／[基本設計書 v1.0](../specs/基本設計書_v1.0.md) §3.2「概念ごとに具体商品へ橋渡し」
**関連実装：** `app/js/screens.js`（`App.renderRoadmap`）／`app/js/s3.js`（`App.renderS3`・`buildCandGroup`）／`app/js/state.js`（`App.CTA_LABEL`・画面遷移）

---

## 1. 目的と背景

- 本アプリの骨格は「**概念（何をすればいいか）→ 商品（何を買うか）の2段階提示**」（機能定義書 設計上の重要方針）。
- 現状：S2 のロードマップ（例「洗顔 → 化粧水 → 乳液」）から S3 へは、下部 CTA「具体的な商品の候補を見る」の1導線のみ。S3 に着くと全カテゴリの候補が並ぶため、**「ロードマップの2番目の概念の商品がどれか」をユーザー自身が探す必要がある**。
- S2 の概念ステップから直接「この概念の候補」に飛べれば、設計思想が体験として完成する。

## 2. スコープ

| やること | やらないこと |
| --- | --- |
| S2 の各ロードマップステップに「この概念の候補を見る」補助リンクを追加 | S3 内でのカテゴリ絞り込みUI（フィルタタブ等）の新設 |
| 遷移先で該当カテゴリグループへスクロール＋一時ハイライト | 既存の下部 CTA の削除・変更（主導線は残す） |
| 概念（ロードマップ文言）→ カテゴリ（products.js の category）の対応表 | ロードマップ生成ロジック（#35/#60）の変更 |

## 3. 概念→カテゴリ対応表

ロードマップの概念語（`App.buildRoadmap` が生成）と商品 `category` の対応を **明示的な対応表**で持つ（文字列の部分一致に頼らない）。

```js
// contracts.js に共有定数として追加（共有ファイル→村上要相談）
App.CONCEPT_TO_CATEGORY = {
  "汚れ落とし": "洗顔料",
  "化粧水": "化粧水",
  "乳液": "乳液",
  "軽めの保湿": "乳液",
  "オールインワン": "オールインワン",
  "アフターシェーブ保湿": "アフターシェーブ"
  // …現行 category 値（products.js 実データ）に合わせて確定
};
```

- 対応表に無い概念が来た場合はリンクを出さない（フォールバック＝現行どおり下部CTAのみ）。
- ロードマップの `concept` は `buildRoadmap` が `main.concept` を「・」区切りで連結している（例："汚れ落とし・化粧水・軽めの保湿"）。**ステップ分割の責務は `buildRoadmap` 側にあるべきか**は実装タスク1で確認し、必要なら `RoadmapStep` に `categories: string[]` を持たせる形を優先する（文字列パースより堅牢）。これは contracts.js の型定義変更を伴うため **村上レビュー必須**。

## 4. 画面設計

### 4.1 S2（ロードマップ）

- 各 `.road__item` の末尾に小さなリンクボタンを追加：
  - ラベル案：`「{概念}」の候補を見る →`
  - 主 CTA より弱い階層（ghost スタイル）。1ステップにつき最大1個。
- 1画面1アクション原則との整合：主 CTA（下部 dock）は維持し、補助リンクは **概念ごとの詳細導線**として扱う。全ステップに出すと騒がしい場合は「買う」系ステップ（order: 1）のみに限定する fallback 案を用意する。

### 4.2 S3 遷移後の挙動

1. `App.show("s3")` で通常遷移（タブロック解除の既存ロジックに従う）。
2. `App.renderS3()` 後、該当カテゴリのグループ要素へ `scrollIntoView({ behavior: "smooth", block: "start" })`。
3. 該当グループを 2 秒程度ハイライト（`.is-focused` クラス付与→CSS transition で消滅）。
4. フォーカス管理：該当グループの先頭候補ボタンへ `focus()` を移す（a11y。キーボード利用者が迷子にならないように）。

### 4.3 カテゴリが候補ゼロの場合

- 予算帯によっては該当カテゴリの候補が空（現行の空状態「この予算帯では候補が見つかりませんでした」表示済み）。
- 空の場合も遷移は行い、空状態メッセージまでスクロールする（「無い」こと自体が情報）。

## 5. ロジック設計

```js
/**
 * ロードマップステップ → 遷移先カテゴリの解決
 * @param {RoadmapStep} step
 * @returns {string|null}  products.js の category 値。解決不能なら null
 */
App.resolveStepCategory = function (step) { ... };
```

- `s3.js` の `buildCandGroup` で、グループ見出し要素に `id="cand-group-{カテゴリをエンコードした値}"` を付与（スクロールターゲット）。
- 遷移関数：`App.gotoCategory(category)` を s3.js 側に新設し、screens.js の S2 リンクから呼ぶ。**画面遷移の窓口は既存の `App.show` を必ず通す**（タブ状態・プログレスの整合のため）。

## 6. 挫折させない設計との整合

- 原則1：関係なし。
- 原則2（1日1タスク）：主アクションは下部 CTA のまま。補助リンクは「見る」だけで、新しいタスクを要求しない。
- 原則3（いつでも戻れる）：S3 から S2 への戻りは既存タブで可能。**遷移後にタブ位置を覚えておく必要はない**（state.current は既存どおり更新）。

## 7. アクセシビリティ

- スクロール後のフォーカス移動を必須とする（§4.2-4）。
- ハイライトは色のみに依存しない（輪郭線＋背景の2重表現）。
- リンクボタンは `<button>` で実装し `aria-label` に遷移先を明示（例：「化粧水の候補を見る（商品画面へ移動）」）。

## 9. テスト観点

- 各タイプのロードマップで、全ステップのリンクが正しいカテゴリへ遷移する（6タイプ分）。
- 対応表に無い概念のステップにはリンクが出ない。
- 予算帯 sub（〜1,500円）で該当カテゴリが空 → 空状態までスクロールする。
- スマホ幅でスクロール位置がタブバーに隠れない（`scroll-margin-top` の設定確認）。
- 既存の下部 CTA 遷移が壊れていない（回帰）。

## 10. 未決事項

1. 補助リンクを全ステップに出すか、「買う」ステップのみに絞るか（画面の騒がしさとのトレードオフ）。
2. `RoadmapStep` 型への `categories` 追加は型定義の変更＝共有の約束の変更。村上の判断を仰ぐ。
3. S3 で複合タイプ時（main＋sub 候補）に、リンク遷移先は main 側のみでよいか。
