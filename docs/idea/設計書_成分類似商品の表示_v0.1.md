# 詳細設計書：成分類似商品の表示 v0.1

**プロジェクト：** 田島組 卒業制作（男の身だしなみアプリ）
**対象機能：** S3 商品候補・比較への「成分が近い商品」表示
**版：** v0.1 / 2026-08-31（**チーム合意前の提案ドラフト**。実装決定ではない）
**根拠：** [プロダクト改善意見 v0.1](./プロダクト改善意見_v0.1.md) §1 強み1／[ヒアリング記録 2026-06-09](../research/interview_tajima_2026-06-09.md) §9「ブランドが違うだけで成分がほぼ同じ商品の情報が刺さる」
**関連実装：** `app/data/products.js`（`ingredients` 配列）／`app/js/contracts.js`（`App.buildCompareTable`）／`app/js/s3.js`（候補・比較描画）

---

## 1. 目的と背景

- 上床先生ヒアリングの示唆：「ブランド名が違うだけで成分がほぼ同じ商品が存在し、若い世代には『このブランドとこれは成分がほぼ同じ』という情報が刺さる」（§9）。「低評価レビュー重視・偽物警戒」と並ぶ、商品選びの信頼性の柱。
- コアペルソナは予算〜5,000円、サブペルソナは〜1,500円。**「高い方と安い方で成分がほぼ同じ」が分かれば、安い方を選ぶ根拠になる**。
- 本アプリの強みは「成分の有無という事実ベース比較」。類似表示はその延長線上にあり、新しい評価軸（効能・安全スコア）を持ち込まずに実現できる。

## 2. スコープ

| やること | やらないこと |
| --- | --- |
| 商品ペアの「成分タグの一致度」を事実として算出・表示する | 「同じ効果がある」「こっちが得」等の断定・優劣表現 |
| S3 の比較表・候補カードへの表示 | 類似度を使った推薦順位の入れ替え（推薦ロジック #37 は変更しない） |
| 手動整備データ（products.js）内での完結 | 全成分配合量・濃度の比較（データに無い＋薬機法リスク大） |

## 3. 用語と表現の確定（薬機法ガードレール）

| 使う表現（許容） | 使わない表現（禁止） |
| --- | --- |
| 「成分タグが ◯/◯ 個共通」 | 「成分がほぼ同じ」（断定に聞こえるため※見出しのみ文脈次第） |
| 「成分の組み合わせが近い」 | 「効果は同じ」「代わりになる」 |
| 「価格差があります」（事実） | 「こちらがお得」（優劣） |

- 見出し案：**「成分タグが近い組み合わせ」**（事実の並記）。行ラベルは「共通する成分タグ ◯個／全◯種」と分数表記にし、解釈はユーザーに委ねる。
- 表現の最終確定は [薬機法準拠ガイドライン](../guidelines/薬機法準拠ガイドライン_v1.0.md) に照らし、たかとが一次レビューする。

## 4. ロジック設計

### 4.1 類似度の定義

成分タグ集合の **Jaccard 係数** を使う（実装が単純で、発表時に説明可能）。

```
similarity(A, B) = |A ∩ B| / |A ∪ B|    （A, B = 商品の ingredients 配列の集合）
```

- 閾値：**0.8 以上**を「近い」とする初期値（データ30-50件で試算して調整。定数 `SIMILARITY_THRESHOLD` として切り出す）。
- 比較対象は **同一 category 内のみ**（化粧水同士など。カテゴリをまたぐ類似は初心者に意味をなさない）。
- 配合量は扱わない（products.js の `ingredients` は有無タグのみ。この限界は発表でも明示する）。

### 4.2 関数IF（contracts.js に追加・純粋関数）

```js
/**
 * 同一カテゴリ内で成分タグが近い商品ペアを返す。
 * @param {Product[]} products  対象商品（通常は S3 表示中の候補）
 * @param {number} [threshold=0.8]
 * @returns {Array<{a: Product, b: Product, shared: string[], score: number}>}
 *   shared = 共通成分タグ名の配列。score 降順。
 */
App.findSimilarPairs = function (products, threshold) { ... };
```

- 配置：`app/js/contracts.js` 下部の実装スタブ群に追加（`App.buildCompareTable` の隣）。
- 依存：`products.js` の `ingredients`（文字列配列）のみ。ingredients.js（事実タグ辞書）の表示名解決には現状依存しない（タグ名はそのまま表示用文字列）。

### 4.3 計算量

候補は画面表示で最大〜12件（カテゴリ×3件程度）。同一カテゴリ内のペア総当たりで高々十数組。**パフォーマンス懸念なし**。

## 5. 画面設計（S3 への追記）

### 5.1 表示案A：比較表への行追加（主案）

- ユーザーが2〜3件を比較中のとき、比較表の末尾に行を追加：
  - 行ラベル：「共通する成分タグ」
  - 値：ペアごとに「◯個／全◯種」（3件比較時は最大ペアを代表表示）
- 既存の `CompareRow` 型（`{label, values, differs}`）に収まるため、**buildCompareTable の戻り値構造は変えない**（行追加のみ）。既存UIへの侵入が最小。

### 5.2 表示案B：候補カードのバッジ（副案）

- 候補カードに「似た成分の候補があります」バッジ＋タップで相手候補にスクロール。
- 実装コストが上がるため **まず案Aのみ**で検証し、ユーザーテストで反応が良ければ検討。

### 5.3 空状態

- 閾値を超えるペアが無い場合は**行自体を出さない**（「類似なし」と表示してノイズにしない）。

## 6. データ設計

- **追加データ不要**。`products.js` の既存 `ingredients` 配列のみで算出する。
- ただし現状のタグは「無香料」「低刺激」等の属性タグも混在する。類似判定の精度を上げたい場合、将来 `ingredients` を「成分系タグ」と「属性タグ」に分離する検討は別Issueとする（本設計では全タグを対象とする最小実装）。

## 7. 挫折させない設計との整合

- 原則1（抜けてもOK）：関係なし（記録系に触れない）。
- 原則2（1日1タスク）：S3 の主アクション「比較して1本決める」を邪魔しないよう、**比較表の中の1行**に留める。新しいボタン・画面は増やさない。
- 原則3（いつでも戻れる）：表示のみの追加で、遷移・ロックに影響しない。

## 8. アクセシビリティ

- 比較表は `role="table"` 済み。追加行も同じ行構造（`role="row"`）で実装し、スクリーンリーダーで「共通する成分タグ ◯個」と読み上がることを確認する。
- 「近い」ことを色だけで伝えない（`is-diff` 強調と同様、テキストで表現）。

## 10. テスト観点

- 成分が完全一致する2商品 → score 1.0 で必ず検出される。
- 共通成分ゼロのペア → 表示されない。
- カテゴリをまたぐペア（化粧水×乳液）→ 表示されない。
- 比較2件／3件それぞれで行が崩れない（PC・スマホ幅）。
- 「効果は同じ」等の禁止表現がUI文言に混入していない（PRチェックリストに薬機法観点を追加）。

## 11. 未決事項（チームに確認したいこと）

1. 閾値 0.8 の初期値は妥当か（商品データ実測で判断したい）。
2. 属性タグ（無香料・低刺激）を類似度計算に含めるか（含めると「無香料が共通」だけで持ち上がる可能性）。
3. 発表資料での説明方法（Jaccard 係数という語を出すか、「タグの一致率」とだけ言うか）。
