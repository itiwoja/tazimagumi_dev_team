# 企画書 v3.0 に対する問題点の洗い出し

## 1. 技術的な穴：楽天 API の「明日」問題

最も緊急度が高いのは、API の切り替えタイミングです。

### 「24 時間の猶予」しかない実装期限

企画書には「旧版 API が 2026 年 5 月 13 日に廃止」とあります。本日は 5 月 12 日ですので、実質的に明日、旧版での実装はすべて動かなくなります。新版（accessKey 方式）への移行が「11 月まで」ではなく、「今すぐ」完了していないと、開発初期のデータ取得テストすらままならない状態です。

### レート制限の壁

楽天 API の新版は「1 秒 1 リクエスト」という厳しい制限があります。23 問の診断結果から複数の商品をマッチングさせる際、逐一 API を叩くと UI がフリーズする恐れがあります。「手動マスター DB」を主力にし、API は価格情報の更新程度に留める設計を徹底しないと、デモ中にエラーを吐くリスクが高いです。

---

## 2. コンテンツ制作の穴：300 SKU の「泥沼」

「手動で 200〜300 SKU をキュレーションする」というタスクが、5 人チームにとって最も重い「隠れたコスト」になっています。

### 成分データの転記コスト

「化粧品成分オンライン」等から成分情報を転記するとしていますが、1 商品あたり全成分（20〜40 種類）を正しく DB 化し、それぞれに「刺激配慮スコア」や「効能タグ」を紐づける作業は、1 人（たかと氏）の負担としては過大です。

### データの鮮度管理

化粧品は頻繁にリニューアル（成分変更）されます。11 月の発表時に手動 DB の情報が古くなっていると、美容に詳しい審査員から「この成分は旧型では？」と突っ込まれる「穴」になります。

---

## 3. 薬機法の穴：コミュニティ機能の「諸刃の剣」

「学内クローズド」にしたことで法的リスクを下げていますが、アプリとしての魅力とのトレードオフが発生しています。

### 「体験談」が書けないコミュニティの虚無感

薬機法上、化粧品で「ニキビが治った」等の体験談を書くことは原則禁止されています。AI で表現をガチガチに制限すると、ユーザー同士の会話が「使用感がいいですね」といった無難な内容ばかりになり、「わざわざこのアプリで話す意味」が失われる危険があります。

### Before/After 写真の「負の側面」

ローカル保存に限定したのは賢明ですが、ユーザーが「全然変わらない（効果がない）」と感じた際、それをネガティブな感情としてコミュニティに書き込むリスクへの対策が不足しています。

---

## 4. 差別化の穴：「男性専用」の定義

競合（LIPS, @cosme）との差別化を「男性専用」に置いていますが、UI/UX における「男性らしさ」の定義がまだ抽象的です。

### 「6 タイプ即決 UI」の根拠

「迷ったらこれ」という導線は初心者には親切ですが、専門学校の卒業制作としては、なぜ「この 6 つの分類」なのかという科学的・市場的根拠をより強固にする必要があります。

### 「卒業システム」の矛盾

「ライン使いから個別最適へ卒業させる」という構想は面白いですが、アプリ側としては「卒業（個別最適化）」された方がデータ管理コストが上がり、アフィリエイト収益の導線も複雑になります。ビジネスモデルとユーザー体験が相反する「穴」が残っています。

---

## 💡 穴を埋めるためのアドバイス

- **たかと氏の救済（AI 活用）:** 成分表の写真を OCR で読み取り、成分 DB と照合して自動でタグ付けする「内部向け管理ツール」を、バックエンドのひろと氏が作成することを検討してください。手入力は必ず破綻します。
- **「明日」への対応:** 今日の放課後、チーム全員で楽天 API 新版の認証が通るか確認してください。
- **診断ロジックの「見える化」:** 11 月の中間発表では、アプリの画面だけでなく、「23 問の回答がどう数値化されて推薦に繋がっているか」の計算式（ロジックシート）を展示できるように準備しておきましょう。それが「中立性」の最大の証明になります。

企画の方向性は非常に「勝てる」位置にいます。特に「髭剃りケア独立モード」は、大手の LIPS などが手を出せていないニッチかつ強力な武器になるはずです。
