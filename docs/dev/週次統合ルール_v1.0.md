# 週次統合ルール v1.0

**プロジェクト：** 田島組 卒業制作（男の身だしなみアプリ）
**関連：** Issue #110 #105 #41 #80 #109 ／[ブランチ運用ルール](./ブランチ運用ルール_v1.0.md)
**ステータス：** 提案（チーム合意待ち）

> 統合を「8月中旬の一大イベント（#41）」から「毎週の習慣」に変え、develop を常に
> **通しデモ可能**な状態に保つためのルール。#105 で判明した「ロジックが画面から一度も
> 呼ばれないまま数週間進む」問題（ビッグバン統合の失敗パターン）を構造で防ぐ。

---

## なぜ必要か

診断ロジック（23問前提）とUI（5問）が別々の前提で並行実装され、**ロジックが一度も画面から
呼ばれないまま**数週間進んでいた（#105）。原因は個人のミスではなく「統合は #41 でまとめて
やる」という**計画構造**にある。このままだとロードマップ（#35）・推薦（#37）でも同じ乖離が
起きる。8月末のビッグバン統合は卒制が失敗する典型パターン。

---

## ルール（5点）

1. **毎週金曜を統合日にする**
   その週にマージされた分を含め、develop で「初回チェック→結果→ロードマップ→比較→記録」の
   通しデモを、誰か1人が実際に触って確認する（5分でよい）。手順は下の「通しデモ・チェックリスト」。

2. **動かない develop を翌週に持ち越さない**
   通しで壊れていたら、翌週の各自の作業より**修正を最優先**する。

3. **ロジック実装のPRは「画面から呼ぶ最小結線」まで含める**
   純粋関数だけ作って未結線のままマージしない（#33 の再発防止）。
   デモ画面・`console` 出力でもよいので「呼ばれている」状態にしてからマージする。

4. **常に実URLで確認できる状態を作る**
   #80（Cloudflare Pages 自動デプロイ）を使い、developで通しデモを確認した変更をmainへリリースした後、公開URLでも確認できるようにする。

5. **確認結果を週次で1行残す**
   本Issue（#110）のコメントか Discussions に「7/12 通しOK / SC-03がダミーのまま」程度を残す。

---

## 通しデモ・チェックリスト（5分・毎週金曜）

`app/index.html` を開いて上から順に。壊れていたら「動かない項目」を1行メモして #110 に残す。

- [ ] **S1 初回チェック**：5問を最後まで選べる／「←」で戻れる／最後に「プランを見る」で S2 へ
- [ ] **S2 ロードマップ**：診断後に表示される（結線後は診断結果が反映されるか）
- [ ] **S3 商品比較**：予算トグルで件数が変わる／比較表が出る
- [ ] **S4 継続記録**：今日のドット・週次評価が押せて保存される（リロードで復元）
- [ ] **設定**：やり直し／削除／（あれば）書き出し・プライバシーが開く
- [ ] **コンソールにエラーが出ていない**（DevTools → Console）
- [ ] mainへのリリース後、実URL（Cloudflare Pages）でも同じことを1回（#80 導入後）
