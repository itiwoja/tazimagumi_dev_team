# ブランチ運用ルール v1.0（メンバー向け）

**プロジェクト：** 田島組 卒業制作（男の身だしなみアプリ）
**対象：** チームメンバー全員（Git初心者OK）／AIエージェント（Codex・Claude）
**関連：** [コーディング規約・命名規則](../guidelines/コーディング規約_命名規則_v1.0.md)・[ガントチャート v2.2](../schedule/ガントチャート_v2.2.md)

> このファイルは「**どこに・どんな名前でブランチを作り、どう出すか**」の決まりです。迷ったらこれを見ればOK。
> AIエージェント向けの機械可読ルールは末尾の `yaml` ブロックにあります（ルート `AGENTS.md` と同内容）。

---

## 0. 3行まとめ

1. **必ず `develop` から**自分のブランチを切る（`main` からは切らない）。
2. ブランチ名は **`feature/自分の担当`**（半角英数とハイフンだけ・日本語禁止）。
3. 完成したら **PRを `develop` に向けて出す**。直接 `develop`/`main` に push しない。

---

## 1. ブランチの全体像

```
main      ← 完成版だけ（さわらない・PRのみ）
 └ develop ← みんなの統合先。ここから切って、ここへ戻す
      ├ feature/sc01-check-ui          （れん）
      ├ feature/sc02-roadmap-ui        （れん）
      ├ feature/diagnosis-logic        （ひろと）
      ├ feature/roadmap-logic          （ひろと）
      ├ feature/recommend-logic        （たかと）
      ├ feature/sc03-product-compare-ui（ゆうと）
      ├ feature/sc04-record-ui         （ゆうと）
      └ 基盤・共有部品                  （村上）
```

- **`main`**：リリース（完成）専用。保護されています。
- **`develop`**：開発の合流地点。**新しいブランチはここから切る／PRはここへ出す**。
- **`feature/*`**：1人が1機能を作る作業ブランチ。

## 3. ブランチ名のルール

- 形式：**`<type>/<内容>`**（例：`feature/sc01-check-ui`）
- `type` は **`feature` / `fix` / `docs` / `chore` / `refactor`** のどれか。
- 使える文字：**半角の英小文字・数字・ハイフン `-` だけ**。
  - ❌ 日本語、空白、大文字、`_`（アンダースコア）は使わない。
  - ✅ `feature/sc01-check-ui` ／ ❌ `feature/初回チェック` ／ ❌ `Feature/SC01`
- **1ブランチ＝1つの機能/タスク**（あれもこれも詰め込まない）。

## 4. 作業の手順（コピペでOK）

> **毎回、専用の作業ディレクトリ（worktree）を分けてから始める。** メインの作業ディレクトリで直接ブランチを切り替えない。単独のタスクでも例外にしない。

### ① 最新の develop を取り込む
```bash
git switch develop
git pull
```

### ② worktree（専用ディレクトリ）を作って移動
```bash
git worktree add ../wt-sc01-check-ui -b feature/sc01-check-ui develop
cd ../wt-sc01-check-ui
```
（`sc01-check-ui` のところを自分の担当名に変える。worktreeは**リポジトリの外**、兄弟ディレクトリに作る）

### ③ コードを書く → 保存（コミット）
```bash
git add .
git commit -m "feat: 初回チェックの選択肢を追加"
```
- コミットメッセージは **`種類: 内容`**。種類は `feat`（機能追加）/ `fix`（修正）/ `docs`（書類）/ `refactor`（整理）/ `test` / `chore`。

### ④ GitHubに上げる（初回は `-u` を付ける）
```bash
git push -u origin feature/sc01-check-ui
```
（2回目以降は `git push` だけでOK）

### ⑤ PR（プルリクエスト）を出す → `develop` に向ける
- 画面に出るURL（`...pull/new/...`）を開く、または GitHub の「Compare & pull request」を押す。
- **base（出し先）が `develop` になっているか必ず確認**（`main` ではない）。
- タイトルと「何をしたか」を簡単に書いて作成。
- コマンドで出すなら：
```bash
gh pr create --base develop --title "feat: 初回チェックUI" --body "やったこと: ..."
```

### ⑥ マージ後のあとしまつ
- PRがマージされたら、使い終わったworktreeを片付ける：
```bash
cd ../../<元のリポジトリ>
git worktree remove ../wt-sc01-check-ui
```
- 次の作業の前に **また①（develop を pull）** からやり直し、新しいworktreeを作る。

---

## 5. やってはいけないこと（重要）

- ❌ `main` や `develop` に**直接 push**しない（必ずPR経由）。
- ❌ `main` からブランチを切らない（`develop` から切る）。
- ❌ 1つのブランチに**複数の機能**を混ぜない。
- ❌ 共有ファイル（`app/css/style.css`・`app/js/state.js`・`app/js/main.js`＝基盤）を勝手に大きく変えない。変えたい時は**村上に相談**（基盤は村上が管理）。
- ❌ ブランチ名に**日本語・空白・大文字**を使わない。
- ❌ worktreeを使わず、メインの作業ディレクトリで直接ブランチ作業をしない（毎回 `git worktree add` から始める）。

---

## 6. よくあるトラブル

| こまった | こうする |
| --- | --- |
| 間違って `main` から切った | `git switch -c 正しい名 develop` で develop から切り直す |
| `develop` が古いと言われた | `git switch develop && git pull` してから自分のブランチに `git merge develop` |
| 変更を消したくない | コミット（`git add .` → `git commit`）してから操作する |
| コンフリクト（衝突）が出た | あわてず村上に共有。1機能1ブランチを守ると起きにくい |
| PRの出し先が main になってた | PR画面の base を `develop` に変更 |

## 7. AIエージェント向け 機械可読ルール（AGENTS.md と同期）

```yaml
# branch-rules: tazimagumi_dev_team
protected_branches: [main, develop]
base_branch: develop        # 新規ブランチは develop から作成
pr_target: develop          # PR は develop に向ける
release_branch: main        # main へは develop からのPRのみ
naming:
  pattern: "<type>/<kebab-scope>"
  allowed_types: [feature, fix, docs, chore, refactor]
  charset: "a-z 0-9 -"      # 小文字英数とハイフンのみ。日本語/空白/大文字/_ 禁止
  one_branch_one_task: true
worktree:
  required: true            # 毎回のタスクで git worktree を使う（並行作業に限らない）
  location: outside_repo    # 例: ../wt-<scope>（リポジトリ内には作らない）
feature_branches:
  - { branch: feature/sc01-check-ui,           owner: ren-1222 }
  - { branch: feature/sc02-roadmap-ui,         owner: ren-1222 }
  - { branch: feature/diagnosis-logic,         owner: kuro1020 }
  - { branch: feature/roadmap-logic,           owner: kuro1020 }
  - { branch: feature/recommend-logic,         owner: takato9310 }
  - { branch: feature/sc03-product-compare-ui, owner: yourenputianjian-sketch }
  - { branch: feature/sc04-record-ui,          owner: yourenputianjian-sketch }
  - { branch: base-and-shared,                 owner: itiwoja }   # 基盤・共有部品は村上
shared_files_owner: itiwoja   # app/css/style.css, app/js/state.js, app/js/main.js は村上が一次管理
commit:
  format: "<type>: <summary>"
  allowed_types: [feat, fix, docs, refactor, test, chore]
workflow:
  - git switch develop
  - git pull
  - git worktree add ../wt-<scope> -b <type>/<scope> develop
  - cd ../wt-<scope>
  - 実装してコミット（commit.format に従う）
  - git push -u origin <type>/<scope>
  - gh pr create --base develop
  - レビュー後にマージ → ブランチ削除 → git worktree remove ../wt-<scope> → 各自 develop を pull
forbidden:
  - main や develop への直接 push
  - main からのブランチ作成
  - 1ブランチへの複数機能の混在
  - ブランチ名への日本語・空白・大文字・アンダースコア
  - worktreeを使わずメインの作業ディレクトリで直接ブランチ作業すること
```

### 7.1 各AIツールがルールを読む場所

メンバーが使う AI コーディングツールごとに、標準指示（このルール）を読み込む場所が異なる。取りこぼしを防ぐため、正本の `AGENTS.md` に加えて Antigravity 用のワークスペースルールを置いている。

| ツール | 読む場所 | 備考 |
| --- | --- | --- |
| Claude Code | `CLAUDE.md`（リポジトリ直下） | `AGENTS.md` と同内容 |
| Codex | `AGENTS.md`（直下） ／ `~/.codex/AGENTS.md`（各自グローバル） | ネストした `AGENTS.md` もカスケードで合成 |
| Antigravity | `.agents/rules/*.md`（常時オン） ／ `AGENTS.md` | `.agents/rules/branch-worktree.md` に本ルールの要点を再掲 |

- **正（Single Source of Truth）は `AGENTS.md`**。`.agents/rules/branch-worktree.md` は Antigravity 向けの再掲であり、齟齬があれば `AGENTS.md` を優先する。
- 「ルールを読む」＝「worktree を必ず切る」ではない（実行環境・エージェント任せ）。機械で強制できる部分（ブランチ名・base=develop・直push禁止）はブランチ保護＋PR Check CI で担保する。

## 8. Service Worker キャッシュ更新ルール（Issue #107）

GitHub Pages 公開後、Service Worker のキャッシュが古いまま残ると、修正をデプロイしても利用者に反映されない。これを構造で防ぐ。

- **`app/` 配下（`css/`・`js/`・`data/`・`index.html`・`manifest.webmanifest`・`icons/`）を変更する PR は、`app/sw.js` の `CACHE_NAME` を必ず +1 する。**
- 抜けは PR チェック CI（#81）の「SW cache bump guard」が機械的に検出して fail させる。
- 新しいアセットを追加したら、`app/sw.js` の `APP_SHELL` にも登録する（初回オフライン時の欠落を防ぐ）。読み込み順は index.html と揃える。
