## 2. システム全体構成

### 2.1 構成方針

- フロントエンド単体（PWA）＋ BaaS（Supabase）の2層構成。**専用バックエンドサーバは作らない**。
- **MVPは素のWeb技術（HTML/CSS/バニラJS・ビルドなし）で構築する**。まず動くものを完成させることを最優先し、フレームワーク導入による複雑さを避ける（実装：`app/`、`window.App` 名前空間）。
- **技術スタックの移行（React 等）はMVP完成後・時間に余裕がある場合の任意ステップ**とする（§2.4）。中間発表時点ではバニラJS版で完結させる。
- 診断スコアリング・ロードマップ生成・推薦は **フロントの純粋関数（JS）**で完結させる（中間発表での説明可能性とデモ安定性を優先）。
- 商品データ・成分タグ・診断ロジックは**差し替えやすく分離**する（保守性要件。将来の移行も容易にする）。
- 中間発表では**外部API（楽天API等）に依存しない**。手動整備の30-50商品で動作させる。

### 2.2 構成図（論理）

```
┌──────────────────────────────────────────────┐
│ クライアント（PWA / ブラウザ・スマホ）            │
│                                                │
│  HTML + CSS + バニラJS（ビルドなし）            │
│  ※将来移行候補：React + Vite + TS（§2.4）        │
│  ┌────────────┐  ┌──────────────────────────┐ │
│  │ UI層        │  │ ロジック層（純粋関数）      │ │
│  │ 4画面       │→ │ ・診断スコアリング          │ │
│  │             │  │ ・ロードマップ生成          │ │
│  │             │  │ ・商品推薦・フィルタ        │ │
│  └────────────┘  └──────────────────────────┘ │
│  ┌──────────────────────────────────────────┐ │
│  │ ローカル保存：IndexedDB / localStorage      │ │
│  │ （診断結果・継続記録・画像はサーバ送信しない）│ │
│  └──────────────────────────────────────────┘ │
└───────────────┬──────────────────────────────┘
                │ supabase-js（読み取り中心）
                ▼
┌──────────────────────────────────────────────┐
│ Supabase（BaaS）                                │
│  ・PostgreSQL（products / ingredients 等）      │
│  ・Auth（MVPでは匿名／任意ログイン）            │
│  ・Storage（MVPでは未使用）                      │
│  ・RLS（読み取り公開・書き込み制限）             │
└──────────────────────────────────────────────┘
        ┊（将来構想）楽天API・OCR連携はMVP対象外
```

### 2.3 技術スタック（MVP＝バニラJS）

| レイヤー | 採用技術（MVP） | 本書での設計上の役割 |
| --- | --- | --- |
| フロント | HTML + CSS + バニラJS（ビルドなし／`window.App` 名前空間・IIFE） | 4画面UI・PWA配信。実装：`app/` |
| ロジック | JS 純粋関数 | 診断・ロードマップ・推薦（テスト容易・説明可能） |
| BaaS/DB | Supabase（Postgres + Auth + Storage + RLS） | 商品・成分マスターの提供。`supabase-js` で接続（読み取り中心） |
| ローカル保存 | IndexedDB / localStorage | 診断結果・継続記録の保持（サーバ送信しない） |
| アクセシビリティ | WCAG 2.1 AA 意識 | 文字大きめモード・コントラスト比 4.5:1 以上 |

> 実装方式の詳細は [コーディング規約・命名規則](../guidelines/コーディング規約_命名規則_v1.0.md)・[状態管理・ルーティング設計](../dev/状態管理・ルーティング設計_v1.0.md) を参照。

### 2.4 技術スタック移行方針（MVP完成後・任意）

- **段取り**：①バニラJS版でMVPを完成・中間発表 → ②時間に余裕があれば技術スタックを移行する。
- **移行候補**：React + Vite + TypeScript（＋必要に応じ Tailwind / shadcn/ui）。
- **移行を容易にする現状の設計**：UI（描画）とロジック（純粋関数）を分離し、データ取得をリポジトリで隠蔽している（[データアクセス設計書](../dev/データアクセス設計書_v1.0.md)）。ロジック・データ層はそのまま再利用し、UI層から段階的に置き換える。
- **判断基準**：移行はMVPの動作・デモ安定性を損なわない範囲でのみ行う。中間発表前は着手しない。

## 4. データ設計（論理モデル）

### 4.1 方針

- **マスターデータ（商品・成分）は Supabase に置き、読み取り中心**で使う（差し替え容易・保守性）。
- **ユーザー由来データ（診断回答・結果・継続記録）はローカル保存**（プライバシー要件：センシティブ情報をサーバ保存しない）。
- 商品には診断タイプタグ（type1〜type6）を必ず付与。複合タイプ対応のため**1商品に複数タグ可**。

### 4.2 主要エンティティ（Supabase 側）

| テーブル | 主な列（論理） | 説明 |
| --- | --- | --- |
| **products** | id, name, brand, category（汚れ落とし/化粧水/乳液/オールインワン等）, price, volume, budget_tier（core/sub）, type_tags（type1〜6の配列）, summary_one_liner, image_url | 手動整備の30-50商品。MVPの中核マスター |
| **ingredients** | id, name, fact_tag（56効能の範囲内の事実タグ）, note | 成分の事実情報。安全性評価は持たせない |
| **product_ingredients** | product_id, ingredient_id, present（有無） | 商品×成分の中間テーブル（成分タグの有無を表現） |
| **roadmap_concepts** | id, type, step_order, concept_label（汚れ落とし等）, timing（today/tonight/morning） | タイプ別ロードマップの概念ステップ定義 |

### 4.3 ローカル保存データ（クライアント側）

| キー | 内容 |
| --- | --- |
| `diagnosis_answers` | SC-01 の23問回答 |
| `diagnosis_result` | `{ primaryType, secondaryType, isComposite, scores, topContributors }` |
| `continuity_log` | 週次自己評価の履歴 |
| `prefs` | 文字大きめモード等のUI設定 |

### 4.4 RLS / 権限方針

- products / ingredients / 関連テーブル：**読み取りは公開**、書き込みは管理者（チーム運用）に限定。
- ユーザーデータはサーバに置かないため、ユーザー単位のRLSは MVP では最小限。

## 5. 診断処理フロー設計（REQ-01 → REQ-02）

> 詳細配点・質問文は [診断ロジック設計書 v1.1](./診断ロジック設計書_v1.1.md) を正とする。本節は処理の流れと責務分割を定義する。

### 5.1 処理ステップ

```
[SC-01 回答配列]
   ↓ DiagnosisService.calculateScores()
6軸スコア集計（皮脂/乾燥/炎症/髭剃り/加齢/初心者度）→ 各軸 0〜100 にクリップ
   ↓ DiagnosisService.determineType()
Step3 例外ルール（S_beginner>=60 / 最高<30 → タイプ⑥）
Step4 最高スコア軸 = 第一タイプ
Step5 同点優先：S_shave>S_inflam>S_oily>S_dry>S_aging>S_beginner
Step6 第一・第二の差≤10pt → 複合フラグ（第二まで・⑥が第二なら単独）
   ↓
結果オブジェクト { primaryType, secondaryType, isComposite, scores, topContributors }
   ↓ RoadmapService.build()
roadmap_concepts からタイプ別の概念手順（today/tonight/morning）を生成 → SC-02
```

### 5.2 責務分割

| モジュール | 責務 | 担当（企画書 §8） |
| --- | --- | --- |
| `DiagnosisService` | スコア集計・タイプ判定 | ひろと（Supabase・診断ロジック） |
| `RoadmapService` | 判定結果→概念手順の生成 | ひろと／れん |
| SC-01 UI | プログレス・スキップ・バリデーション | れん（フロント） |
| ディスクレーマー共通部品 | 結果・商品画面での常時表示 | 村上（共有コンポーネント） |

## 6. 推薦・比較処理フロー設計（REQ-03/04/05）

```
[SC-02 判定結果 + 予算帯選択]
   ↓ RecommendService.pickCandidates()
products を type_tags（判定タイプ）× budget_tier で絞り込み
   ↓ 概念（category）ごとに少数候補を抽出
[SC-03 候補リスト]
   ↓ ユーザーが最大3点を比較トレイへ
CompareService.buildTable()
価格帯・目的・成分タグ（present の有無）で横並び表
+ 初心者向け「違いの一言」（summary_one_liner）
   ↓
成分は事実（有無）のみ表示。安全/効能の断定なし（§8 準拠）
```

| モジュール | 責務 | 担当 |
| --- | --- | --- |
| `RecommendService` | タイプ×予算での候補抽出 | たかと（データ）／ひろと |
| `CompareService` | 横並び比較表の構築 | ゆうと（比較・継続画面） |
| 成分タグ表示部品 | 事実提示UI | たかと／村上 |

## 7. 非機能設計

| 区分 | 要件 | 本書での設計 |
| --- | --- | --- |
| **法令・表現** | 薬機法準拠 | §8 に集約。表現は56効能の範囲・成分の有無のみ |
| **プライバシー** | センシティブ情報をサーバ保存しない | 診断回答・記録・画像はローカル保存（§4.3）。画像はサーバ送信しない |
| **デモ安定性** | 外部API非依存 | 楽天API/OCRはMVP対象外。確認済み30-50商品で動作 |
| **保守性** | データ・ロジック分離 | products/ingredients をマスター化、ロジックは純粋関数で分離 |
| **使いやすさ** | 3分以内に理解 | プログレス・スキップ・概念先出し・予算帯切替で短縮 |
| **アクセシビリティ** | WCAG 2.1 AA 意識 | 文字大きめモード、コントラスト比4.5:1以上、タップ領域確保 |

## 8. 薬機法準拠の実装方針（横断要件 REQ-05）

- 結果・推薦・成分表示の文言は「効く・治る・消える・最適・保証」等の**断定表現を使用しない**。
- 推薦理由は**客観データ（出典付きランキング等）または成分タグ（56効能の範囲内）**で表現する。
- 成分は**「有無」という事実のみ**を表示し、独自スコアによる安全性・刺激評価はしない。
- ディスクレーマー（診断ロジック設計書 v1.1 §8 の確定文言）を SC-02 / SC-03 の最下部に**共通コンポーネント**として常時表示する。
- 文言は[薬機法準拠ガイドライン](../guidelines/薬機法準拠ガイドライン_v1.0.md)（作成済み）で禁止/許容表現を確定し、たかとが一次管理する。
