# コーディング規約・命名規則 v1.0

**プロジェクト：** 田島組 卒業制作（男の身だしなみアプリ）
**関連：** [状態管理・ルーティング設計](../dev/状態管理・ルーティング設計_v1.0.md)・[データアクセス設計書](../dev/データアクセス設計書_v1.0.md)
**ステータス：** ドラフト（基盤アプリ `app/` の実装方式に準拠）

> 全員が同じ書き方で機能を足せるようにする最小ルール。**基盤（CORE）は触らず、機能はfeatureで足す**のが大前提。

---

## 1. 基盤の構成（前提）

```
app/
├── index.html
├── css/style.css        ← デザイントークン＋全コンポーネント
├── data/products.js      ← 商品マスター（window.PRODUCTS）
└── js/
    ├── state.js          ← [CORE] 状態・進捗・toast（window.App）※触らない
    ├── screens.js        ← 各画面の描画
    └── main.js           ← [CORE] 起動・イベント配線 ※触らない
```

- **ビルドなし**。`index.html` で `data → state → screens → main` の順に読み込む。
- グローバルは `window.App`（状態・関数）と `window.PRODUCTS`（データ）のみ。

> 注：MVPは**バニラJS**（IIFE＋名前空間・ビルドなし）で構築する（基本設計書 §2.3）。新規もこの方式に合わせる。React 等への移行はMVP完成後・任意（基本設計書 §2.4）。

---

## 2. ファイル・モジュールのルール

- 1ファイルはIIFEで包み、`"use strict";` を先頭に。公開物は `App.xxx` か `window.XXX` に限定。
- `[CORE]` とコメントされたファイル（`state.js` / `main.js`）は**書き換え禁止**。拡張は公開関数経由。
- 1ファイル ≤ 400行を目安、最大800行。長くなったら分割。
- 機能の所在をコメントで示す（例：`/* [F-03] 予算トグル */`）。

---

## 3. 命名規則

| 対象 | 規則 | 例 |
| --- | --- | --- |
| 変数・関数 | camelCase | `answeredCount`, `updateProgress` |
| 真偽値 | is/has/should/can 接頭辞 | `isComposite`, `completed` |
| 定数 | UPPER_SNAKE_CASE | `S1_TOTAL`, `SCREENS` |
| サービス（型/概念） | PascalCase | `DiagnosisService` |
| DOM id | camelCase | `progressFill`, `todayDot` |
| CSSクラス | kebab-case（BEM風） | `.qcard`, `.chip__label`, `.tab.is-active` |
| データ属性 | `data-` ＋ 用途 | `data-pick`, `data-budget`, `data-go` |

- 状態クラスは `is-*`（`is-active` / `is-on` / `is-locked` / `is-done`）。

---

## 4. 書き方の原則

- **不変更新**：状態は新しい値で更新し、共有配列/オブジェクトを直接書き換えない。
- **イベント委譲**：親要素で `click` を受け、`closest("[data-*]")` で対象判定（main.js の方式）。
- **早期return** で深いネストを避ける（4段まで）。
- マジックナンバーは定数化（`S1_TOTAL` 等）。
- `console.log` を残さない。デバッグは確認後に削除。

## 6. コミット・ブランチ（チーム運用）

- ブランチ：`feature/<機能>`（例：`feature/s3-compare`）。基盤からfeatureを切る。
- コミット：`feat: / fix: / docs: / refactor:` ＋ 簡潔な説明。
- 共有部品（`style.css` / `state.js`）の変更は村上に相談してから。
