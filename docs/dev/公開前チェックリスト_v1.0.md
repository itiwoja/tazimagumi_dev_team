## 1. 公開ルート互換の静的点検結果（実施済み）

Cloudflare Pages はプロジェクトの公開ルート（`https://<project-name>.pages.dev/`）で公開される。公開物は `app/` の中身であり、URLにリポジトリ名や `/app/` を追加しない。相対パス運用のため、公開ルートが変わってもアセットを解決できる。

| 対象 | 点検方法 | 結果 |
|---|---|---|
| `app/manifest.webmanifest` の `start_url` / `scope` | 目視確認 | ✅ `"./"` （相対）。Cloudflare Pagesの公開ルートでも正しく解決される |
| `app/manifest.webmanifest` の `icons.src` | 目視確認 | ✅ `"./icons/icon-192.png"` 等、すべて相対パス |
| `app/sw.js` の Service Worker 登録パス | `app/index.html` L381 を確認 | ✅ `navigator.serviceWorker.register("./sw.js")` — 相対パス |
| `app/sw.js` の `APP_SHELL`（キャッシュ対象） | 目視確認 | ✅ すべて `"./"` 始まりの相対パス（`./index.html`, `./css/style.css` 等） |
| `app/index.html` の `<link>` / `<script>` タグ | `rg '(src\|href)="/[^/]'` で絶対パス（`/` 始まり）を検索 | ✅ 該当なし（Google Fonts の外部URLを除き全て相対パス） |
| `app/js/*.js` 内の `fetch()` / `new URL()` / 絶対パス参照 | 全JSファイルを検索 | ✅ `debug.js` の `new URL(global.location.href)` のみ（現在地基準の相対解決のため問題なし）。ハードコードされた絶対パスなし |
| アイコンファイルの実在確認 | `app/icons/` を確認 | ✅ `icon-192.png` / `icon-512.png` / `apple-touch-icon.png` すべて存在 |

**結論：現状のコードはCloudflare Pagesの公開ルート互換の観点で修正不要。** 絶対パスに起因する公開後の404リスクは検出されなかった。

## 3. 公開実行の手順（#41・#43 完了後、人間が実施）

1. **Cloudflare Pagesプロジェクトの作成**（管理者操作・初回のみ）
   - Cloudflare Dashboard → Workers & Pages から **Direct Upload** のPagesプロジェクトを作成し、初回作成時にproduction branchを **`main`** に指定する
   - 既存のDirect UploadプロジェクトはDashboardからproduction branch controlsを変更できないため、Cloudflare APIのUpdate Project endpointを一度実行して `main` に更新する
     ```bash
     curl --request PATCH \
       "https://api.cloudflare.com/client/v4/accounts/<ACCOUNT_ID>/pages/projects/<PROJECT_NAME>" \
       --header "Authorization: Bearer <API_TOKEN>" \
       --header "Content-Type: application/json" \
       --data '{"production_branch":"main"}'
     ```
2. **GitHub Actionsの認証情報を登録する**（管理者操作・初回のみ）
   - Settings → Secrets and variables → Actions → Secrets に `CLOUDFLARE_API_TOKEN`（Pages Edit権限）と `CLOUDFLARE_ACCOUNT_ID` を登録する
   - Variables に `CLOUDFLARE_PAGES_PROJECT_NAME`（Pagesプロジェクト名）を登録する
3. **`develop` で通しデモとCI greenを確認した変更を `main` 向けリリースPRとしてマージする**（`main` への直接pushは保護ルールで拒否される）
4. `main` へのマージをトリガーに `deploy-pages.yml` が自動実行される（Actionsで `main` refを選んだ `workflow_dispatch` の手動実行も可能）
5. Actionsの `Deploy to Cloudflare Pages` ステップが成功し、Deployment URLが出力されることを確認する
6. 実URL（`https://<project-name>.pages.dev/` または設定済みカスタムドメイン）にアクセスし、S1→S2→S3→S4 の通しデモが動くか確認する
7. 問題なければ本Issue（#46）をクローズする

> [!WARNING]
> `main` がそのまま本番になるため、**「main にマージする」＝「公開する」** と同義になった。
> 動かない状態を `develop` にも `main` にも入れないこと。`develop` で通しデモとCI greenを確認し、CI redのPRはマージしない（`PR Check` は必須ステータスチェック）。
